## 方式比较与建议

| 方式 | 玩家体验 | 代价与限制 |
|---|---|---|
| 进入交谈先选话题 | 能直达想听的内容 | 改变原默认交谈顺序，普通短对白也要先选，不建议本轮采用 |
| 原对白正常结束后，提供一次可选回应（建议） | 原内容完整保留，玩家可以接话或离开 | 多一个可退出的选择窗；需处理输入释放、取消及旧会话退休 |
| 增加跑腿/帮忙委托 | 能产生持续目标 | 必须定义任务、状态、奖励及存档；超出本候选稿，不进入首轮 |

推荐第二种。尚未由真人选定，本文先给出完整可评审的小范围版本；设计通过不等同于获得实现授权。

## 建议流程

1. 玩家沿原交谈入口走近 NPC，完整播放该人物当前原对白，原文字和顺序不变。
2. 只有原对白自然结束，才显示“想再说点什么？”；可选两句回应或“先告辞”。取消原对白不弹选择窗。
3. 默认焦点为“先告辞”。取消键、关闭按钮和选择告辞都结束会话，不追加台词或产生状态。
4. 选择一句回应后，原姓名和当前真实NPC肖像显示对应的一句反馈。玩家原生推进读完后直接退出，不再循环弹话题窗。
5. 再次交谈按同样流程。没有首次奖励、隐藏完成度、已听计数、跨图记忆或后台冷却，不因多次选择改变任何资格。

菜单会增加一次可以立即退出的操作，这是否值得是待真人决定的体验取舍。若不喜欢交谈后再弹窗，可放弃本提案，已完成的原闲谈不受影响。

### 状态与锁的交接

| 阶段 | 允许动作 | 转移或退休 |
|---|---|---|
| 原对白中 | 原揭示/翻页/取消 | 正常结束转等待释放；取消直接退休 |
| 等待释放 | 维持本会话输入锁，等待确认/E/鼠标旧按压释放 | 新独立输入才可选择；取消或来源失效退休 |
| 选择窗 | 两项回应、告辞、关闭/取消 | 回应只接受一次并先关闭旧窗；其余退休 |
| 反馈中 | 原揭示/翻页/取消 | 无论自然结束或取消，都退休，不再弹选择窗 |
| 已退休 | 不接受任何回调 | 无下一轮；重访创建新会话 |

已核`ExplorationDialogue._on_ended()`的顺序：先移除原`exploration_dialogue_active`，清理布局/临时角色，再同步发`finished`。因此未来会话应在该同步回调中先核身份和是否自然结束，再立即接管原交互锁；实际建窗可以延期，但不能到延期建窗时才首次加锁。这样不把原对白结束至建窗间隙暴露为可移动/可开菜单的一帧。

这一交接仅在本会话捕获的原控制器、一次性结束回调归属、预期结束代次及当前阶段仍匹配（原timeline结束时已清空，不与开始引用直接比较）时成立，不能把任意一次`finished`当作原对白结束。如果同步回调中已有别的会话抢先占用或上下文变化，应退休，不抢锁或修改新会话。会话应保存独立不透明token，在交接点和清理点核归属；不能仅凭一个布尔meta判断锁是谁的。

选择回应时先标记该选择已消费、关闭并脱离旧选择窗，然后重核来源，再调用同一个真实NPC的`play_resident_lines`。旧选择窗的`_exit_tree`不得无条件remove_meta；会话状态已经交给反馈后，旧窗只能清自己。反馈仍由原控制器清自己的锁，之后的会话清理不再清可能属于新对白的锁。不同步直接连用“旧窗queue_free→新对白”，避免旧窗延迟退树误删新锁。

原NPC的`try_interact()`确实同时检查Dialogic.current_timeline与`exploration_dialogue_active`；村庄移动、房门和菜单也依赖原锁链。新token只用于证明归属，不要求全地图改读另一套锁。不能靠增加一个没人读取的新meta，就宣称玩家已经被冻结。

### 输入行为的设计要求

- 原对白最后一次E、确认或鼠标按压必须先释放。窗口显示后第一次独立按压才算选择；按住不产生自动确认，键盘echo不接受。
- 等待释放时，相关按压仍须被本会话接收并标记已处理，不能漏到原村庄取消菜单或邻近NPC。取消在该阶段直接告辞，不要让用户卡在一个无法退出的空档。
- 三个可聚焦动作构成闭合焦点顺序，默认告辞；Tab/Shift+Tab可遍历，原确认执行当前项，取消/标题关闭等价告辞。左右方向是否切按钮沿所选原生控件约定，不能擅自把移动键映射成选项确认。
- 两条长选项必须完整可见；优先沿已有选择窗样式并把响应按钮做清晰分行，不能硬塞三项到底部窄按钮栏后仅做字符估算。具体窗口宽高和实际焦点仍需未来原生验证，本文不编造像素通过值。
- NPC原名与两选项只用于本窗，不显示“任务”“奖励”“已完成”等额外UI；选项本身不再作为玩家新角色对白插入，反馈才用原NPC姓名/肖像，避免无来源玩家肖像。

### 选择控件的具体取舍与拒绝语义

只读核对`ninja_teaching_choice.gd`后，建议选择**CanvasLayer内的原样式PanelContainer与纵向三按钮结构**，参考其VBox组织，但新建普通回应适配，不实例化教学脚本。该教学窗默认聚焦第一项，未来新窗必须明确改为第三项告辞。相比`ConfirmationDialog`底部按钮栏，这样三句较长选项更容易分行展示，也避开原生OK默认键可能越过当前焦点确认的问题；仍需实测，而非已证无穿透。这里是游戏内控件，不新增操作系统原生对话框。

键位按项目action绑定处理，不把E/Z等物理键硬编码到新逻辑。上下及Tab/Shift+Tab在三项内闭环，`interact`/`confirm`以新的独立按压激活当前项；必须避免同一action既手动激活又由Button默认处理，产生两次pressed。取消action/窗口关闭统一走单次告辞。村庄原`menu`/`cancel`都可能开队伍菜单，因此新窗打开或等待释放期间应消费这类输入；Tab作为焦点切换时也要优先于原地图菜单。I/M等原menu输入仅阻止穿透，不重新绑定为话题选择。

鼠标左键只点击实际按钮才选中；窗外遮罩必须实际接收输入，移入不确认，窗外点击不触发寻路或其他NPC。选项按下与随后释放也属于旧选择输入，不能让它继续推进刚打开的反馈；这需要选择→反馈也有独立输入门控，不能只防原文→选择的第一次交接。

普通入口的返回语义必须分清：

| 判定 | 普通入口后续行为 |
|---|---|
| 不是候选身份或未启用此可选方案 | 沿原普通`_show_lines` |
| 是候选、上下文仍有效，但候选数据坏/缺失 | 保原对白，放弃可选部分；不影响原交谈 |
| 已被候选会话接管 | 不再重复调用原`_show_lines` |
| 候选会话已失效/退场/换档 | 退休并视为本次已处理，不回落旧来源原对白 |
